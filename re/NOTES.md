# megademo - reverse-engineering log
## Layout (phase 1, done)
- DEMO.EXE = MZ stub + PMODE/W **1.20** (entry 0x59). `unpack_clean.py` (= unpack_pmodew.py + a hook that dumps RAM the moment the program entry is reached, so the dump is *clean*, i.e. before the CRT/MIDAS touched any variable):
  `ENTRY=0x59 python3 unpack_clean.py 80 ../DEMO.EXE 0x261b 0x340 mem.bin` (user-site unicorn, no `python -I`). `gunzip -k mem.bin.gz` gives the 64 MB dump `mem.bin` used by `emucore.py` (not kept unzipped).
- **The live program is the flat object at linear 0x1b000..0x62000** (`low.bin` = linear 0x10000.., `low.dis` = objdump -M intel, VMA 0x10000; code uses absolute linear addresses, DS base 0, selector 0x858 in PM). The 0x100000 copy (`image.bin`) is the *unrelocated* load image (offsets relative to the object): do not disassemble it for addresses. (An old `image.dis` of it was deleted.)
- Entry `_cstart` = 0x27d20 (Watcom, `jmp 0x27d98`). `main` = 0x1bff0. Libs: Watcom CRT, MIDAS-like sound lib (0x23xxx-0x26xxx, S3M loader reads via int21), and a small **retrace-locked timer lib at 0x27936-0x27ca1** (PIT calibration against port 0x3da, ISR 0x27682 on int 8 calls callback 1 at start of vertical retrace, callback 2 after it). Only callback used: `0x1be10 = inc dword [0x52888]` => **one tick per vsync (70.086 Hz in mode 13h)**.
- Video: **VGA mode 13h, 320x200, linear 0xA0000, DAC palette via ports 0x3c8/0x3c9** (mode-X registers never touched). Pixels are not square: display at 4:3.
- Init (main 0x1bff0): 0x21dc6 allocs 0x3d3263 bytes (DPMI 0501) and reads **DATA.DAT whole** (open 0x1e168, read 0x1e172) -> so "TITANICS-cruncher decrunches while loading" (string in the CRT area) is a leftover, DATA.DAT is stored raw. Then MIDAS loads MUSTAKS.S3M (0x2673c, handle at 0x562e0), mode 13h, timer start (0x27ba3).
## Main loop pattern (0x1c087..0x1c75c)
Straight-line list of ~17 stages. Each stage: `init(); do { snap=[0x52888]; i=0; while([0x52888]-[0x5288c] > i){ 0x1be68(); update(); i++ } [0x5288c]=snap; render() } while([0x4ab11] < N)`; `end()`.
- `0x1be68` = poll the player: `MIDASgetPlayStatus` (0x24194) fills a struct whose [0]=**order (position)** -> `[0x4ab11]`, [8]=row -> `[0x4ab15]`. Every stage ends on a S3M **order** threshold (pos < N). So scenes are exactly tied to S3M orders; update = fixed 70 Hz logic step, render = once per loop (so rendering speed does not change the animation, only smoothness).
- Stage table (update / render fn, ends at order N; `hook` = address of `mov [0x5288c],eax`, used by the harness as frame boundary). Times from the golden run (K=7, 10 fps virtual):

## DATA.DAT (done)
Not an archive: one blob; 24 offsets in a table at 0x4ab1d (relocated by the load address in the init loop at 0x21dd6) index into it. `extract_data.py` cuts them into `assets/NN_offset_size.bin` (+PNG previews): 0 and 6 RIX3 256x256 (ColoRIX) images; 16 RIX3 320x200 (people at a bar, with palette); 3, 10-15, 22 = 320x200 PCX (brain/face/logo/"orange1996 c est la fin voila"); 1, 7, 19 = 128x128 raw 8-bit (textures/light maps); 2, 8, 9, 18, 20, 23 = 64000 raw 8-bit 320x200 (megablast logo etc.); 5 (128000), 21 (112000), 17 (69020) = unknown tables/LUTs; **4 = 2.8 MB unknown stream (probably the helicopter sequence)**. PLASTI3D.PCX = 512x512 8-bit PCX (cracked-stone texture, used by the vortex stage via 0x231c4).
## Emulation harness (done, runs the whole demo)
- `emucore.py` (from b-hyper: flat GDT, LDT, int21/int31 DPMI, bump arena, file I/O for DATA.DAT/S3M/PCX by name; GDT now 512 entries so selector 0x858 works). `harness.py` `Golden`: stubs 0x27936 (calibration), 0x27ba3 (timer start), 0x24194 (getPlayStatus -> order/pattern/row from s3mtime.json at the virtual time), VGA ports (0x3da pattern, palette 0x3c8/9). Virtual clock: at every stage's `[0x5288c]=snap` (16 hooks + the PCX stage loop 0x1c33a) the frame is captured and `[0x52888]` += K (K=7 default = 10 fps virtual, K=1 would be 70 fps) and the music position is advanced by K ticks. No music is played/emulated; MIDAS hardware init is not reached (calibration stubbed, sound device never probed in this path).
- `golden.py OUT T0 T1 STEP [K]` -> `golden/tNNNN.NN.png` (320x200) + `stages.txt` (time, hook, order). `sheet.py` makes contact sheets. `golden/` = full demo every 2 s (144 frames, K=7). Speed ~1.1-2 s wall per demo second. `s3mtime.py`, `extract_data.py` as above.
## Caveats / not done
- K=7 gives 10 fps captures; the logic runs at 70 Hz inside (7 updates per render) so frames are right for the grid but intermediate renders are not captured. No bit-exact claim yet (no reference other than the emulator itself; PIT/retrace values are fake, 17030 counts/frame).
- The tick rate 70.086 Hz is assumed (retrace-locked callback); stage lengths are determined by S3M order anyway.
- Effects only identified visually, no per-effect analysis yet; none of the update/render functions are decompiled.

# Session 2 (port started): oracle, timeline, first bit-exact effect
## Timeline cross-check (done)
`tools/mk_timeline_openmpt.py`: libopenmpt (ctypes, `set_position_order_row` + `get_position_seconds`) vs the own S3M walker `s3mtime.json` (kept as `s3mtime.model.json`, it drove the Unicorn clock): **all 3435 rows reachable exactly, max difference 0.338 s (0.1 %), last row 326.13 s model vs 325.79 s libopenmpt**. The web player uses libopenmpt times (`re/s3mtime.openmpt.json`, `web/fx/timeline.js`); demo end = order 0x34 row 0 = 284.90 s. The model-vs-openmpt gap means the S3M position the original saw in the golden run (model) can be up to 0.3 s off the audio the web player plays; effects are keyed to (order,row), so they stay locked to the music, only the within-stage tick count is re-derived from the openmpt row time.
## Stage list with start (order,row) (from the golden run hook hits, `web/timetable.js`)
Stages 1..17 = fx00..fx16: all start on row 0 of the order in the table above, except fx02 (light rays ends on a flag set by its update at ~order 5, so fx03 starts at (5,12) only as read on the 10 fps golden grid: +-0.1 s, **not derived**).
## Per-frame oracle `fx_oracle.py` (done)
Generic: `STAGE=<frame hook> NEXT=<next stage hook> UPD=<update fn> REND=<render fn> RET=<ret of render> K1ORDER=<order from which K=1> STATE=addr:size,.. OUT=x.npz python3 fx_oracle.py`. K=7 (fast) until K1ORDER, then K=1 (one tick = one update + one render, 70 fps). Stores per render: `n` = updates run since the beginning of the stage (hook at the update fn entry), virtual `ticks`, order, row, STATE words (read at render entry), `idx` (VRAM 0xA0000 right after the render's last `ret`, i.e. after the VRAM copy) and `pal` (DAC, 6-bit). `tools/oracle2bin.py` converts for node. Run time: ~400 s to reach order 38 + stage. NB: the clock is only advanced at the frame hooks, so frames are exact functions of `n`; the real original's `n` at a given music time depends on timing (loop `updates = tick - last`), the port uses n = floor((t - t_stage_start) * 70.086) + 1 (oracle: first render has n=1).
## fx13 = stage 14 "crowd - Dali" (update 0x203c4, render 0x201ea, init 0x200de): DONE, see status below
- Data: asset 17 (69020 B) = 7 RLE frames of 160x100 (RLE: byte&0xc0==0xc0 -> run of (b&63) x next byte, else literal; per frame until exactly 16000 bytes, 0x20163), asset 21 (112000 B) = 320x350 picture ([0x4ab71]), palette = static .data 0x469ec (6-bit, set once at init, no fades), sine table = static dwords at 0x3705e (4096 entries, -1023..1023). `tools/export_fx13.py` -> `web/assets/fx13.bin` (190 KB).
- Update (per tick): `[47200]=min(n,0x4b0)` (picture scroll, >>3 = rows, so 0..150 rows over 350), `[46610]=n%14` (anim frame, >>1), `[46cec]=(n*0x20)&0xfff`. All three verified against the oracle STATE for 1538 frames.
- Render: `A=(sine[[46cec]]+0x400)>>3, B=0x100-A`, LUT_A[i]=(i*A>>8)&255, LUT_B[i]=(i*B>>11)&255; 0x20454 builds a 320x200 buffer from the 160x100 frame (rows 6..193 only, 2x horizontally and vertically with word ops incl. the cross-byte carry of `add ax,bx`, `and 0x3f3f`); pixel = LUT_A[buf] + LUT_B[pic[scroll+p]] (8-bit wrap).
- Seek class: **pure function of n** (all three counters are closed forms), so seek = compute n from the music time: exact by construction, no replay, no checkpoints.
### fx13 status: NOT fully bit-exact, honestly
`node tools/fx13check.mjs oracle.bin` (oracle = 1538 frames, order 38 row 0 .. order 42, n=1..1538): **palette 0 differing bytes; 161 differing pixels in 161 frames (of 1538 x 64000 = 98.4 M px), always the same pixel (x=314,y=193)**, only in frames where the anim frame is 6 (n%14 in {12,13}). Cause: 0x20454's last output row reads `[esi+0xa0]` one row (160 B) past the end of the 7 decoded frames, i.e. past the original's own 112000-byte buffer (the DPMI block `0x2af90` is even 112 B + the page slack shorter than 64000+112000). My port reads 0 there. At the first render the oracle's memory past the buffer is also all zeros (dump `OOB=512`), yet the value the original needs at that pixel is not constant over time (implied BUF byte 12/13 at n=12, 9 at n=26, 8 at n=40, 6 at n=54, 5 at n=68), so something writes into that memory later (not identified: not found in the time left). Not guessed: left as the 1-pixel difference. Next: watch writes to 0x20627f80+0..0x200 (UC_HOOK_MEM_WRITE) during the stage.

## fx12 = stage 13 "checker tunnel" (update 0x206c1, render 0x20659 -> 0x20526, init 0x205a1): DONE, bit-exact
- Assets: 5 = 320x200 words (per-pixel texture offsets, [0x4ab31]), 6 = RIX 256x256 texture + palette, 7 = shade table 16 KB (`tools/export_fx12.py` -> `web/assets/fx12.bin`); motion table static dwords at 0x47506.
- Update per tick: fade 47bc6 += 4 (to 0x100); shade level 47bf6 += 2 (to 0xb0, only after the first render: flag 47bf2); camera 47bda/47bde += (t[2o+2]*ce + t[2o]*d2)>>8 resp. (t[2o+3]*ce + t[2o+1]*d2)>>8 (o = order, ce 0.. up, d2 256.. down, reset on an order change); si = (da>>4) + ((de>>4)<<8) as a word.
- Render: screen = tex[(OFF + si) & 0xffff]; for the first 200 columns shade[(47bf6>>3)<<8 | c] is written to the second 256x256 buffer (stride 256), then the buffers swap (feedback). Palette = base * 47bc6 >> 8.
- Oracle: `STAGE=1c5ac NEXT=1c612 UPD=206c1 REND=20659 RET=206c0 K1ORDER=24 STATE=47bc6:4,47bf6:1,47bda:4,47bde:4,47bce:4,47bd2:4,47bd6:4,47204:2,47be2:4,47be6:4 OUT=re/oracle_fx12.npz python3 fx_oracle.py` (5 min), then `tools/oracle2bin.py`.
- Seek class: ACCUMULATING (feedback). `render` replays from the stage start (<= ~800 ticks) and caches the last frame (render() itself advances the buffers, so it must run once per tick).

## fx14 = stage 15 "bar photo + megablast logo" (update 0x22b1c, render 0x227ea, init 0x22602; ends order 0x2e): DONE, bit-exact
